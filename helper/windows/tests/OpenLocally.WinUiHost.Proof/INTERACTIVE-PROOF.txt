CreatorCrate integrated manual visual proof

Run from the repository root:

powershell -NoProfile -ExecutionPolicy Bypass -File .\helper\windows\tests\OpenLocally.WinUiHost.Proof\run-manual-visual-proof.ps1 -PostingState Ready -Theme Dark

PostingState accepts Ready, Confirming, Unknown, or Posted. Theme accepts Dark or Light. Recommended visual-gate launches:

-PostingState Ready -Theme Dark
-PostingState Confirming -Theme Dark
-PostingState Unknown -Theme Dark
-PostingState Posted -Theme Dark
-PostingState Ready -Theme Light

Each launch opens the actual NativeManualPublishingCompanion with the production WinUI RichEditBoxes, native Buttons, Platform ComboBox, Assets ListView/Header, and footer. Use the real Platform ComboBox to inspect Patreon, X, and Bluesky. The fixture is fully local and does not use a server or network.

The Assets table contains representative production-model data: two available images with real Shell thumbnails, one available text attachment, and one actually unavailable image. The available rows begin selected (3 of 4 selected). Use the real ListView with click, Ctrl+click, and Shift+click to inspect row selection, count changes, unavailable guidance, responsive columns, and the one intentionally long filename/path.

F6 is not implemented. Theme is selected at launch and applies through the production whole-window refresh path to native chrome and both WinUI islands together.

Genuine Windows High Contrast acceptance uses this sequence:

1. Launch the production manual proof normally, preferably with -Theme Dark.
2. Keep that production companion window open.
3. Enable a genuine Windows Contrast Theme in Windows Settings.
4. Wait for the real Windows settings-change notification.
5. Inspect the SAME live production companion window for High Contrast readability.
6. Optionally disable the Contrast Theme while the window remains open and verify that production refreshes again.

There is no launcher -Theme HighContrast argument. The -Theme Dark and -Theme Light arguments select proof presentation only; neither substitutes for genuine Windows High Contrast. High Contrast acceptance depends on the real Windows settings-change path after launch. Do not simulate High Contrast through proof arguments.

Manual visual checklist:

- Overall CreatorCrate feel; release title versus metadata; Content hierarchy.
- Platform selector; Patreon title/body; X and Bluesky post editors; emoji and Unicode.
- Copy versus Mark-as-posted hierarchy; posting status, helper, action, and footer aggregate.
- Assets heading; all four fixture rows visible without vertical scrolling; populated thumbnails; File, Role, Size, Status, and Path / staged name columns. More than five rows may use the native vertical scrollbar.
- Selected-row appearance; initial 3 of 4 count; count and guidance after click/Ctrl+click/Shift+click, including selecting the unavailable row.
- Responsive columns and long-value clipping/scroll behavior; footer; no bright native patches.
- Dark and Light whole-window consistency.
- Ready, Confirming, Unknown/Retry, and Posted production presentations.

Additional manual accessibility gates (not completed by automated proof):

- With the proof already open, enable a genuine Windows Contrast Theme and repeat the visual/readability checks on that same live window.
- Test Windows Text Size at 100%, 125%, 150%, 200%, and the highest practical setting.
- At 96, 144, and 192 DPI, repeat default and elevated Text Size checks. If available, move the window between physical mixed-DPI monitors and verify crisp text, stable bounds, focus, and selection.
- With Narrator, verify platform content, read-only state, control names, and focus movement.
- Verify Tab/Shift+Tab, text selection/copy/navigation, scrolling, Escape, and non-editability.

Important scope boundary: the production multi-file drag path is proven by a real physical drop into a browser/web destination: all three initially selected available assets arrived in Release/list order regardless of which selected row began the drag. The original one-file result is not reproducible as a generalized CreatorCrate source defect. Individual social-site acceptance remains destination-specific.

Package B local OLE drop-target proof

Run from the repository root:

powershell -NoProfile -ExecutionPolicy Bypass -File .\helper\windows\tests\OpenLocally.WinUiHost.Proof\run-manual-visual-proof.ps1 -DragProof

This opens the actual production NativeManualPublishingCompanion and a separate test-only local IDropTarget. The fixture creates these available paths in stable Release/list order:

0. campaign-cover.bmp
1. launch-assets\final-approved-media\creatorcrate-autumn-product-launch-behind-the-scenes-wide-preview.bmp
2. posting-notes.txt

The fourth row, missing-community-photo.png, is genuinely unavailable. The console prints the full generated absolute paths for the current run.

Primary interactive proof:

1. Confirm rows A+B+C (ordinals 0+1+2) are selected; do not select unavailable row D.
2. Click-hold and drag ANY one selected row from the production ListView onto the local target.
3. Release over the target.
4. Read DROP PASS/FAIL, origin, count, effect, and exact received path order in the console.

Expected for origins A, B, or C: count=3 and paths 0,1,2 in Release/list order. The target requests COPY and only inspects the received CF_HDROP; it does not copy, move, or write files.

Secondary cases:

- Ordinary single-click B intentionally collapses selection to B. Drag B and expect one received path: ordinal 1.
- Starting with A+B selected and C unselected, drag C and expect C only.
- If unavailable D is selected with available rows, production rejects the whole selection before OLE delivery. The target receives no Drop.
- Ctrl/Shift selection remains native Windows ListView behavior.

Use a real mouse pointer. First click the local target and confirm it displays CLICK RECEIVED, then perform the drag; clicking does not simulate a drop. Do not invoke a test command or synthesize LVN_BEGINDRAG. Close the production companion to end the proof; the target registration, both windows, fixture files, controller, and process are then cleaned up. This local harness is diagnostic infrastructure, not a prerequisite for the already proven generic browser/OLE contract. Patreon, X, and Bluesky acceptance remains destination-specific.

WP10D interactive desktop test set

The deterministic Windows-helper gate is:

powershell -NoProfile -ExecutionPolicy Bypass -File .\helper\windows\tests\run-deterministic-gate.ps1

It runs the normal helper suite, including deterministic UIA contracts, and excludes tests explicitly marked Category=InteractiveDesktop or Category=DiagnosticStress. InteractiveDesktop proofs require foreground interaction; DiagnosticStress tests are excluded separately because they are intentionally long-running diagnostics.

From the repository root, run on an unlocked foreground-capable Windows desktop:

dotnet test .\helper\windows\tests\OpenLocally.Tests\OpenLocally.Tests.csproj -c Release --no-restore --filter "Category=InteractiveDesktop"

This explicitly classified test exercises physical UIA focus, SendKeys input rejection, InvokePattern.Invoke(), and ComboBox ExpandCollapse transitions/item enumeration. It is excluded from the deterministic helper gate because those operations depend on foreground desktop access. All UIA provider, control type, name, enabled, focusable, Text/Selection/Invoke/ExpandCollapse pattern, read-only, current selection, and production-structure assertions remain in the deterministic test.
